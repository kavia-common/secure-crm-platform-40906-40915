# Partitioning and Sharding

## Purpose
Provide strategies for scaling data via native PostgreSQL partitioning and, when necessary, sharding patterns. Focus on time- and tenant-based criteria aligned with CRM workloads.

## Scope
- Native partitioning criteria and DDL
- Routing strategies and constraints
- Sharding considerations and pros/cons
- Operational practices

## Partitioning in PostgreSQL

### Criteria
- Time-based:
  - interactions by month or quarter on occurred_at.
  - audit_logs by month on created_at.
- Tenant-based (if multi-tenant):
  - Partition by tenant_id hash or list for customer, SR, complaints tables.
- Hybrid:
  - For very high volume: tenant -> time subpartitioning.

### Example DDL: Time Partitioning (Monthly Interactions)
```sql
-- Parent table
CREATE TABLE IF NOT EXISTS interactions (
  id uuid PRIMARY KEY,
  customer_id uuid NOT NULL,
  channel text NOT NULL,
  subject text,
  summary text,
  occurred_at timestamptz NOT NULL,
  source_ref text
) PARTITION BY RANGE (occurred_at);

-- Partition creation helper example
CREATE TABLE IF NOT EXISTS interactions_2025_11
  PARTITION OF interactions
  FOR VALUES FROM ('2025-11-01') TO ('2025-12-01');

-- Indexes on partitions
CREATE INDEX IF NOT EXISTS ix_interactions_2025_11_customer_time
  ON interactions_2025_11(customer_id, occurred_at DESC);
```

### Example DDL: Hash Partitioning by Tenant
```sql
CREATE TABLE IF NOT EXISTS service_requests (
  id uuid PRIMARY KEY,
  tenant_id uuid NOT NULL,
  customer_id uuid NOT NULL,
  type text NOT NULL,
  priority text NOT NULL,
  status text NOT NULL,
  sla_due_at timestamptz,
  assigned_to uuid,
  created_at timestamptz NOT NULL DEFAULT now()
) PARTITION BY HASH (tenant_id);

CREATE TABLE IF NOT EXISTS service_requests_p0 PARTITION OF service_requests FOR VALUES WITH (MODULUS 8, REMAINDER 0);
CREATE TABLE IF NOT EXISTS service_requests_p1 PARTITION OF service_requests FOR VALUES WITH (MODULUS 8, REMAINDER 1);
-- ... up to p7
```

## Routing Strategy

### Application Routing
- Ensure INSERT/SELECT predicates include partition keys:
  - For time partitions: include occurred_at in writes or default to now().
  - For tenant partitions: always include tenant_id in where clauses and joins.
- Use BEFORE INSERT triggers only when unavoidable; prefer explicit columns for performance.

### Maintenance
- Pre-create upcoming partitions (e.g., next 6 months).
- Detach and archive old partitions; leverage ATTACH/DETACH for archival work without locking parent.
- Run ANALYZE on new partitions post-creation.

## Constraints and Caveats
- Foreign keys across partitions can be limited; consider co-locating partitioning strategy across related tables.
- Global unique constraints require workarounds (e.g., application-level guarantees or sequences with tenant prefix).
- Index maintenance applies per partition—monitor bloat and plan reindex windows.

## Sharding Considerations

### When to Shard
- Single node limits reached (I/O, storage, CPU) after optimization and partitioning.
- Multi-region latency requirements.

### Shard Key Options
- tenant_id (preferred in multi-tenant).
- customer_id hashed, if tenant not used.
- Avoid time as shard key by itself for write hotspots.

### Pros and Cons
- Pros: Horizontal scale, regional locality, blast radius reduction.
- Cons: Cross-shard joins complexity, global transactions, operational overhead, rebalancing complexity.

### Routing Patterns
- Directory-based routing service: map tenant_id to shard connection string.
- Library-based consistent hashing: map key -> shard.
- Read replicas per shard for scale-out reads.

- RFP: Scalability, HA/DR, performance requirements.
