# Data Lifecycle and Retention

## Purpose
Define end-to-end data lifecycle controls for the CRM platform, covering classification, consent, retention schedules, deletion strategies, archival processes, and regulatory compliance across environments.

## Scope
- Data classification and identification of PII and sensitive fields
- Lawful basis of processing (consent vs legitimate interest)
- Retention schedules by entity and supporting archival strategies
- Soft and hard delete semantics and purge workflows
- GDPR-analogous and DPDP Act-aligned requirements and notes
- Non-production masking and data minimization guidance

## Data Classification

### Classification Levels
- Public: Non-sensitive reference data and documentation.
- Internal: Operational non-PII data (e.g., enumerations, workflow definitions).
- Confidential: Business data without PII but with operational sensitivity (e.g., workflow runs, SR metadata).
- Restricted (PII/Financial): Personally Identifiable Information and sensitive attributes (e.g., customers, contact points, interactions content when containing PII, complaint narratives). Encryption and masking required.

### PII and Sensitive Fields
- customers: name, dob, government_id/tokenized_id, risk_rating, kyc_status (sensitivity depends on content), address lines, pii_encrypted (JSONB envelope containing sensitive attributes).
- contact_points: phone, email, address data, value_enc holds encrypted value.
- interactions: free-text summary may include PII; subject and payloads must be redacted/masked where possible; attachments must be scanned and classified.
- users: emails and phone numbers are PII; password hashes are sensitive security data.
- audit_logs: must not contain PII beyond identifiers; diff_json must omit sensitive field values or store hashed/masked deltas.

## Lawful Basis and Consent
- Consent: Marketing communications, optional contact mechanisms, and channel subscriptions require explicit consent records with timestamp, scope, and versioned policy text references.
- Legitimate Interest: Core service execution (service requests, complaints handling) under contractual necessity or legitimate interest is permissible. Ensure opt-out is honored for non-essential processing.
- Records of Processing: Maintain table consent_events(entity_type, entity_id, consent_type, scope, granted, source, occurred_at) to capture consent lifecycle. Policy references stored via policy_ref and version.

## Retention Schedules

### Recommended Schedules (subject to legal counsel and regulator)
- customers: active + 7 years after last interaction (for audit/regulatory), subject to legal hold.
- contact_points: align with customers; obsolete contacts may be purged 24 months after replacement if not needed for audit.
- interactions: 24–36 months; longer if linked to open SR/complaints; apply legal hold where applicable.
- service_requests: 7 years from closure.
- sr_activities: 7 years from linked SR closure.
- complaints: 7–10 years from closure for regulatory alignment (IGMS/SEBI guidance), confirm locally.
- complaint_escalations: 7–10 years from resolution.
- workflows/workflow_runs: executions retained 24 months; metadata definitions retained while active + 24 months.
- knowledge_articles: latest plus historical versions retained indefinitely; archive superseded versions after 24 months.
- audit_logs: 7–10 years (audit requirements and SEBI-aligned posture).
- sessions/auth artifacts: 90–180 days typical; tokens shorter (hours/days) as per security posture.
- report_jobs and exports: 90 days; longer only when justified.

Record retention schedule changes in data_retention_policies(version, effective_from, rationale, approver, policy_doc_ref) and log enforcement runs.

## Deletion Strategies

### Soft vs Hard Delete
- Soft Delete: For operational rows that require recoverability and audit linkages (customers, SRs, complaints). Implement deleted_at timestamp and deleted_by. Apply row-level security (RLS) to hide soft-deleted rows from standard roles.
- Hard Delete: For transient artifacts (staging tables, idempotency keys older than horizon), after retention expires and no legal hold applies.

### Purge Workflows
- Daily job evaluates retention cutoffs per entity; excludes rows under legal hold.
- Multi-phase purge:
  1) Stage purge candidates into purge_queue(entity_type, entity_id, reason, scheduled_for).
  2) Apply cascading deletes following FK constraints with ON DELETE CASCADE where permissible; otherwise perform ordered deletes by dependency graph.
  3) Write purge_audit(entity_type, entity_id, policy_version, purged_at, purged_by_job, hash_before) capturing structural hashes without PII.
- Attachments: Securely delete blobs and remove references; verify deletion and remove from CDN/object storage.

## Archival and Tiering
- Warm Archive: Partitioned historical tables (e.g., interactions older than 12 months) retained in cheaper storage with read-only access and limited indexes.
- Cold Archive: Compressed, encrypted exports (e.g., ZSTD + AES-256 envelope using KMS) stored in backup vaults with strict access controls and catalog metadata (checksums, ranges, policy refs).
- Rehydration: Documented process to restore archived partitions for legal discovery. All rehydration must be logged with purpose, approver, and retention of access evidence.

## GDPR/DPDP Alignment Notes
- Right of Access: Provide export via views with masking (no secrets, keys, or security artifacts). Response time per lawful requirements.
- Right to Rectification: Audit rectifications via audit_logs; enforce business validation.
- Right to Erasure: Where lawful (not overriding regulatory retention), execute anonymization or hard deletes post-retention; maintain non-identifying tombstones to evidence compliance.
- Data Minimization: Default to collect only necessary PII fields; design APIs and forms to avoid free-text PII where structured fields exist.
- Purpose Limitation: Tag data with purpose where feasible; enforce in data access services.
- Cross-Border: Ensure data residency within India when mandated; document sub-processors and regions used.

## Non-Production Data Handling
- Masking: Use deterministic tokenization/masking for referential integrity across tables; never use raw PII.
- Subsetting: Create minimal representative subsets; exclude rare categories that risk re-identification.
- Access: Enforce least privilege; time-bound approvals; audit all exports/imports.

## Example SQL Snippets

### Soft Delete Pattern
```sql
ALTER TABLE customers ADD COLUMN IF NOT EXISTS deleted_at timestamptz;
ALTER TABLE customers ADD COLUMN IF NOT EXISTS deleted_by uuid;

-- Example soft delete
UPDATE customers SET deleted_at = now(), deleted_by = :actor_id WHERE id = :id;
```

### Purge Queue
```sql
CREATE TABLE IF NOT EXISTS purge_queue (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  entity_type text NOT NULL,
  entity_id uuid NOT NULL,
  reason text NOT NULL,
  scheduled_for timestamptz NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now()
);
```

### Legal Hold
```sql
CREATE TABLE IF NOT EXISTS legal_holds (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  entity_type text NOT NULL,
  entity_id uuid NOT NULL,
  hold_reason text,
  placed_at timestamptz NOT NULL DEFAULT now(),
  released_at timestamptz
);
```
