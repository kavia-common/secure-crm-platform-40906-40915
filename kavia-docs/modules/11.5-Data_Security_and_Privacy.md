# Data Security and Privacy

## Purpose
Define database-layer and application-layer controls to ensure confidentiality, integrity, and availability of CRM data with a focus on PII protection and least-privilege access.

## Scope
- Field-level encryption strategies
- Key management practices
- Row-Level Security (RLS) policy patterns
- Non-production masking
- Data minimization and auditability

## Field-Level Encryption

### Approaches
- Database-level (pgcrypto):
  - Encrypt sensitive columns (e.g., contact_points.value_enc) using pgp_sym_encrypt with KMS-provisioned keys retrieved via application.
- Application-level envelope encryption:
  - Encrypt at service layer with DEK per field/record wrapped by KEK from KMS; store ciphertext + metadata (alg, key_id).

Example:
```sql
-- Example with pgcrypto (ensure extension enabled)
CREATE EXTENSION IF NOT EXISTS pgcrypto;

-- Encrypt insert
INSERT INTO contact_points (id, customer_id, type, value_enc)
VALUES (gen_random_uuid(), :customer_id, :type, pgp_sym_encrypt(:plaintext, :key, 'cipher-algo=aes256'));

-- Decrypt select (restricted views)
SELECT pgp_sym_decrypt(value_enc, :key) FROM contact_points WHERE id = :id;
```
Do not expose decryption in generic views; prefer service-level decryption and masking.

## Key Management
- Use cloud KMS or HSM-backed keys for KEK; rotate KEKs annually and on incident.
- Store DEKs per record or per tenant; rotate DEKs via re-encryption batch jobs.
- Maintain key usage logs; never log key material; secure secrets via vault.

## Row-Level Security (RLS)

### Enable and Patterns
- Enable RLS on PII-bearing tables; create policies per role.
```sql
ALTER TABLE customers ENABLE ROW LEVEL SECURITY;

-- Example policy: agents may see rows only for their tenant and not soft-deleted
CREATE POLICY customers_agent_tenant ON customers
  FOR SELECT USING (
    tenant_id = current_setting('app.tenant_id')::uuid
    AND deleted_at IS NULL
  );

-- Supervisors: broader access with masking applied by view
CREATE POLICY customers_supervisor ON customers
  FOR SELECT USING (tenant_id = current_setting('app.tenant_id')::uuid);
```
- Set app.tenant_id via SET LOCAL in connection on auth; restrict SET rights.

### Masking via Views
- Create role-specific views to mask sensitive fields.
```sql
CREATE VIEW v_customers_masked AS
SELECT id, master_customer_no, left(name, 1) || '***' AS name_masked, created_at
FROM customers;
```

## Non-Production Masking
- Automated ETL step to tokenise PII before import.
- Deterministic hashing or format-preserving tokenization to maintain joins and testability.

## Data Minimization
- Design DTOs to include only necessary fields by default.
- Avoid free-text PII in interactions; use structured fields.

## Auditability
- Append-only audit_logs capturing actor, action, entity, and non-sensitive diffs.
- Hash-chain optional for tamper-evidence.
- Guard rails: no PII in audit; reference IDs only.

## Example RLS Bootstrap
```sql
-- Session bootstrap example (app side)

SET ROLE crm_app_read;
```
