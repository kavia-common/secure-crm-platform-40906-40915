# Indexing and Performance

## Purpose
Define a pragmatic indexing strategy and performance guardrails for core CRM tables, including compound and partial indexes, maintenance routines, and query patterns aligned with expected workloads.

## Scope
- Table-by-table index guidance
- Compound, partial, and covering indexes
- Maintenance (VACUUM/ANALYZE/reindex) procedures
- Query patterns, pagination strategies
- Read scaling via replicas

## Index Strategy by Table

### customers
- Primary key: id (uuid).
- Lookup: master_customer_no unique index.
- Search: lower(name) text pattern ops if name search is supported.
- Access by identity: last_interaction_at (desc) for recent activity lists.

Example:
```sql
CREATE UNIQUE INDEX IF NOT EXISTS ux_customers_master_no ON customers(master_customer_no);
CREATE INDEX IF NOT EXISTS ix_customers_name_trgm ON customers USING gin (lower(name) gin_trgm_ops);
CREATE INDEX IF NOT EXISTS ix_customers_last_interaction ON customers (last_interaction_at DESC);
```

### contact_points
- Access: customer_id, type; uniqueness on normalized value when required.
```sql
CREATE INDEX IF NOT EXISTS ix_contact_points_customer ON contact_points(customer_id, type);
-- For deterministic normalized value field 'value_norm' if maintained
CREATE UNIQUE INDEX IF NOT EXISTS ux_contact_points_value ON contact_points(type, value_norm);
```

### interactions
- Access: customer_id + occurred_at desc, channel filters.
- Partial index: open or unresolved interactions if flagged.
```sql
CREATE INDEX IF NOT EXISTS ix_interactions_customer_time ON interactions(customer_id, occurred_at DESC);
CREATE INDEX IF NOT EXISTS ix_interactions_channel_time ON interactions(channel, occurred_at DESC);
```

### service_requests
- Access: customer_id, status, priority, sla_due_at (SLA boards), assigned_to.
- Partial index: only active statuses to keep index small.
```sql
CREATE INDEX IF NOT EXISTS ix_sr_customer ON service_requests(customer_id);
CREATE INDEX IF NOT EXISTS ix_sr_assign_status ON service_requests(assigned_to, status);
CREATE INDEX IF NOT EXISTS ix_sr_sla_active ON service_requests(sla_due_at) WHERE status IN ('New','InProgress','Pending','Escalated');
```

### sr_activities
- Access: sr_id, created_at desc.
```sql
CREATE INDEX IF NOT EXISTS ix_sr_activities_sr_time ON sr_activities(sr_id, created_at DESC);
```

### complaints
- Access: customer_id, status, severity, regulator_flag, created_at.
```sql
CREATE INDEX IF NOT EXISTS ix_complaints_customer ON complaints(customer_id);
CREATE INDEX IF NOT EXISTS ix_complaints_status_created ON complaints(status, created_at DESC);
CREATE INDEX IF NOT EXISTS ix_complaints_regulator ON complaints(regulator_flag) WHERE regulator_flag = true;
```

### complaint_escalations
- Access: complaint_id, level, escalated_at desc.
```sql
CREATE INDEX IF NOT EXISTS ix_complaint_escalations_comp_level ON complaint_escalations(complaint_id, level, escalated_at DESC);
```

### audit_logs
- Access: created_at (time-range), actor_id, entity_type+entity_id.
- Partial: by action classes to reduce index bloat.
```sql
CREATE INDEX IF NOT EXISTS ix_audit_time ON audit_logs(created_at DESC);
CREATE INDEX IF NOT EXISTS ix_audit_actor_time ON audit_logs(actor_id, created_at DESC);
CREATE INDEX IF NOT EXISTS ix_audit_entity ON audit_logs(entity_type, entity_id, created_at DESC);
```

### workflows/workflow_runs
```sql
CREATE INDEX IF NOT EXISTS ix_workflow_runs_entity ON workflow_runs(entity_type, entity_id, started_at DESC);
CREATE INDEX IF NOT EXISTS ix_workflows_active ON workflows(active) WHERE active = true;
```

## Query Patterns

### Fetch Customer 360
- Pattern: single customer_id -> multiple small queries or one join with filtered ranges.
- Tip: Avoid selecting large text blobs or encrypted fields when not needed; project only necessary columns.

### SR Boards
- Use ix_sr_sla_active and status filters; order by sla_due_at nulls last; paginate with keyset (sla_due_at, id).

### Interactions
- Time-range queries with customer_id AND occurred_at > now() - interval '24 months'.

## Pagination

### Keyset Pagination (Recommended)
- For consistent SLAs and to avoid offset scans on large tables:
```sql
SELECT * FROM interactions
WHERE customer_id = :id
  AND occurred_at < :cursor_time
ORDER BY occurred_at DESC, id DESC
LIMIT :limit;
```

### Offset Pagination (Only for small datasets)
- Acceptable for admin listings with capped size.

## Maintenance Routines

### VACUUM and ANALYZE
- Autovacuum enabled; additionally schedule:
  - Weekly VACUUM (VERBOSE) for heavy-write tables (interactions, audit_logs, sr_activities).
  - Nightly ANALYZE for tables with frequent inserts/updates.

### REINDEX and Bloat Control
- Quarterly reindex for GIN/GIST (name trigram); ad-hoc upon bloat detection.
- Use pg_stat_user_indexes to monitor idx_scan vs idx_tup_read.

### Example Maintenance SQL
```sql
VACUUM (ANALYZE) interactions, audit_logs, sr_activities;
ANALYZE service_requests, complaints;

-- Reindex sample
REINDEX INDEX CONCURRENTLY IF EXISTS ix_customers_name_trgm;
```

## Read Replicas
- Configure one or more streaming replicas (physical replication) for read-heavy workloads:
  - Route analytic/reporting queries and long-running reads to replicas.
  - Ensure replica routing at application layer with role-based connection strings (read_only).
  - Be replica-lag aware; avoid time-sensitive reads on lagging replicas.

## Monitoring and KPIs
- Slow query log threshold: 200ms initial.
- Track p95 per query group (360, SR boards, complaints lookup).
- Alert on sequential scans exploding after plan changes.
