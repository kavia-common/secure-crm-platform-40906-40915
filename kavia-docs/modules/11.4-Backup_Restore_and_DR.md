# Backup, Restore, and Disaster Recovery

## Purpose
Establish an operationally sound data protection strategy for PostgreSQL, including backups, restores, PITR, and DR with clearly defined RPO/RTO targets and security controls.

## Scope
- RPO/RTO targets and strategy mapping
- Physical vs logical backups (pg_basebackup vs dumps)
- WAL archiving and PITR steps
- Restore validation and runbooks
- Backup encryption and access control

## Targets
- RPO: ≤ 15 minutes (via WAL archiving and frequent uploads).
- RTO: ≤ 2 hours for primary site restore under typical dataset sizes (optimize by infra).

## Backup Approaches

### Physical Backups (Recommended for PITR/large DBs)
- pg_basebackup for full base backups.
- Continuous archiving of WAL segments to durable storage (object store).
- Pros: Faster restore with PITR; exact copy of cluster.
- Cons: Requires compatible Postgres version; cluster-level.

### Logical Dumps (Supplementary)
- pg_dump for schema and selective data exports; useful for dev/test refreshes and smaller tables.
- Pros: Portable, selective.
- Cons: Slower full restore; loses MVCC snapshots.

## WAL Archiving
- Configure archive_mode = on and archive_command to push WAL to object storage.
- Ensure archive_command is idempotent and monitored.
- Retention of WAL aligned with backup retention (e.g., 7–30 days).

Example postgresql.conf fragments:
```conf
archive_mode = on
archive_command = 'test ! -f /wal-archive/%f && cp %p /wal-archive/%f'
wal_level = replica
max_wal_senders = 5
```

## PITR Procedure (Runbook)
1) Stop database services on target or ensure clean target cluster dir.
2) Restore latest base backup to PGDATA.
3) Place recovery.signal and recovery parameters (restore_command, recovery_target_time).
4) Start PostgreSQL; monitor recovery to target time; remove signal when complete.

Example recovery.conf (12+ use GUC/standby.signal semantics):
```conf
restore_command = 'cp /wal-archive/%f %p'
recovery_target_time = '2025-11-17 12:30:00+00'
```

## backup_db.sh and restore_db.sh (Repository)
- backup_db.sh: Provides pg_dump-based backups saved to database_backup.sql; tries multiple engines but our platform uses PostgreSQL with port 5000.
- restore_db.sh: Restores from database_backup.sql using psql into postgres; supports other engines for resilience.

Operational note: For production, pair pg_dump logical backups with pg_basebackup + WAL archiving for RPO ≤ 15 minutes.

## Test Restore Runbook
- Frequency: Monthly in lower environment; quarterly full DR drill.
- Steps:
  - Provision fresh VM/container with same Postgres major version.
  - Copy latest base backup and WALs OR latest database_backup.sql.
  - Execute restore_db.sh for logical test OR follow PITR runbook for physical test.
  - Run post-restore validation: schema checksum, counts per major table, sample queries, application smoke tests.
  - Document duration to compare against RTO; log artifacts.

## Encryption of Backups
- At-rest: Encrypt backups using envelope encryption (KMS-managed). For object store, enable server-side encryption and/or client-side with AES-256 GCM.
- In-transit: TLS for uploads/downloads.
- Key rotation: Annual or per policy; maintain key version tracking in backup catalogs.

## Access Controls
- Least privilege IAM roles for backup read/write.
- Break-glass access procedure with approvals and time-bound tokens.
- Audit all access and downloads; store audit evidence with runbook results.

## DR Strategy
- Warm standby with streaming replication to secondary region/site.
- Regular failover drills; measure RPO/RTO.
- Application-level configuration for read-only during failover if needed; feature flags for graceful degradation.
